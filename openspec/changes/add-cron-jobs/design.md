## Context

Two kinds of data currently accumulate with nothing to clean them up:

- **Avatar files on disk** (`AVATAR_UPLOAD_DIR`, default `./uploads/avatars`).
  `UsersService.updateAvatar` writes the new file, then updates
  `User.avatarUrl`, then (if there was an old one) deletes the previous
  file. There's no transaction tying the disk write to the DB write — if the
  process crashes or the DB call fails between them, the new file is orphaned
  on disk with no `User` row pointing at it. Filenames are
  `<userId>-<randomUUID()><ext>`, generated by `avatarFilenameFor` in
  `apps/backend/src/users/avatar-upload.config.ts`.
- **`ProcessedWebhookEvent` rows** (Postgres, via Prisma). `BillingService`
  inserts one per processed Stripe webhook event for idempotency
  (`processedAt` defaults to `now()`), and nothing ever deletes them.

Everything else that looks like "state that should expire" (refresh tokens,
email verification tokens, password reset tokens) already lives in Redis
with a TTL and self-expires — it's explicitly out of scope here.

The codebase has two established conventions this design must follow:
1. **Flat feature modules** under `src/<feature>/` — no nested domain
   layers (see `apps/backend/src/users/`).
2. **`process.env` read directly**, no `ConfigService` injection anywhere,
   even though `ConfigModule.forRoot({ isGlobal: true })` is registered.

## Goals / Non-Goals

**Goals:**
- Delete avatar files on disk that no `User.avatarUrl` references.
- Delete `ProcessedWebhookEvent` rows older than a retention window.
- Run both on a recurring schedule with no HTTP trigger needed.
- Log start/success (with duration and count)/failure for each run, matching
  the existing per-class `Logger` convention.

**Non-Goals:**
- Cleaning up Redis-side state — everything there already has a TTL, except
  the `family:<familyId>` / `user:<userId>:families` sets noted during
  research, which are a separate, unrelated bug (no expiry is ever set on
  them at all) — not "stale after N days," a correctness gap. Out of scope
  for this change; worth its own follow-up.
- A job-history table, admin UI, or `/admin` surface for run results — Step 2
  (admin panel) is later in tech.md and can read logs or add its own storage
  then. This change only needs jobs to run and log, not to persist history.
- Distributed-lock/multi-instance coordination for overlapping cron ticks —
  this app runs as a single backend instance today; adding a lock now would
  be solving a problem that doesn't exist yet.
- Any change to the avatar upload write path itself (e.g. wrapping the
  write+DB-update in a transaction to prevent orphans at the source). The
  cron job is a safety net for the existing window, not a fix for it —
  fixing the root cause is a separate, smaller change if ever prioritized.

## Decisions

**`@nestjs/schedule`'s `@Cron()` decorator, not a BullMQ repeatable job.**
The codebase already has BullMQ wired up (`email`, `chat-reply` queues), so
a repeatable BullMQ job was the alternative. Rejected because: these jobs
have no payload, no per-invocation retry semantics worth queuing for, and no
reason to survive a Redis outage differently than the rest of the app.
`@nestjs/schedule` is the standard Nest-native way to do "run this on a
timer," needs no queue/worker split, and is what tech.md itself names
(`@nestjs/schedule wired into a small CronModule`).

**One `CronModule`, two single-responsibility services.**
`AvatarCleanupService` and `WebhookEventCleanupService`, each with its own
`@Cron()` method and its own `Logger`, rather than one `CronService` with two
methods. Matches the repo's one-concern-per-class shape elsewhere (each
guard does one check, each processor handles one queue) and keeps each job
independently testable.

**Schedule and retention as env-configured constants, `process.env` direct.**
`CRON_AVATAR_CLEANUP_SCHEDULE`, `CRON_WEBHOOK_EVENT_CLEANUP_SCHEDULE` (cron
expressions, default daily at a low-traffic hour) and
`CRON_WEBHOOK_EVENT_RETENTION_DAYS` (default `30`), defined with `?? default`
fallbacks in a new `apps/backend/src/cron/cron.config.ts` — mirrors
`avatar-upload.config.ts` and `billing.config.ts` exactly. No validation
schema, because none exists anywhere else in this codebase to be consistent
with.

**Orphan detection: list-disk-then-diff-against-DB, not DB-then-check-disk.**
`readdir(AVATAR_UPLOAD_DIR)` for the full file list, `prisma.user.findMany`
for every non-null `avatarUrl`, build a `Set` of referenced filenames
(`avatarUrl.split('/').pop()`), delete any disk file not in that set. This
direction is deliberate: a file that exists on disk but isn't referenced is
unambiguously safe to delete (nothing can be pointing at it that this query
would miss, since `avatarUrl` is the only thing that ever references a
filename). The reverse direction (iterate DB rows, check file exists) would
answer a different, less useful question — "which users have a missing
avatar file" — and isn't part of this proposal's scope.

**30-day retention for `ProcessedWebhookEvent`, deleted by `processedAt`
cutoff.**
Stripe retries failed webhook deliveries for up to 3 days
(https://docs.stripe.com/webhooks — general knowledge from the codebase's
existing billing design notes, not re-verified here since it's not the
subject of this change). 30 days is a wide safety margin past that,
generous enough that even a long backend outage followed by Stripe's retry
window can't cause a duplicate event to be reprocessed as "new." The value
is a named constant, not hardcoded inline, so it can be tuned later without
hunting through the service.

**Logging matches the existing ad-hoc per-class `Logger` convention, not a
new abstraction.** Each service gets `private readonly logger = new
Logger(<ClassName>.name)` and logs one line at start, one at success (with
elapsed ms and count of items affected), one at failure (with the error).
No new shared "cron logger" or job-run-tracking utility — the codebase has
no shared logging abstraction anywhere today, and introducing one here would
be scope creep against a two-job feature.

**Failure handling: catch, log, and let the schedule continue — no retry.**
`@nestjs/schedule` has no built-in retry (unlike BullMQ's queue-level
retry); a job that throws simply logs via Nest's unhandled-rejection
handling and waits for its next scheduled tick. This is intentional and
matches Decision 1 (why not BullMQ): these are idempotent, periodic sweeps
where "try again in 24h" is an acceptable and sufficient retry strategy for
this stage of the project. Each service therefore wraps its cron method body
in try/catch itself specifically so a thrown error is logged with context
before Nest's default handling takes over, not to implement retry.

## Risks / Trade-offs

- **[Risk]** A file finishes uploading (written to disk) in the exact
  instant between the orphan-sweep's `readdir` and its `findMany`, and gets
  deleted before the DB row referencing it is committed → user's brand-new
  avatar vanishes.
  **Mitigation:** schedule the sweep at a low-traffic hour (default
  03:00 local) and, more importantly, only delete files whose `mtime` is
  older than a short grace period (e.g. 10 minutes) — anything newer is
  presumed to be an in-flight upload and skipped until the next run.
- **[Risk]** `CRON_WEBHOOK_EVENT_RETENTION_DAYS` set too low by a future
  config change could delete rows Stripe might still retry against,
  reintroducing a duplicate-processing window.
  **Mitigation:** default of 30 days is far past Stripe's actual retry
  window; document the reasoning in the constant's comment so a future
  editor doesn't drop it casually.
- **[Trade-off]** No job-run history is persisted (Non-Goal) — if a cleanup
  silently fails for days, nothing surfaces that except backend logs.
  Acceptable for now since there's no admin UI yet to show it in (Step 2);
  revisit when the admin panel's "Queues" section is built.

## Migration Plan

- Additive only: new module, new env vars with safe defaults, no schema
  migration (no new Prisma model), no changes to existing request paths.
- Deploy by merging; jobs start running on their default schedule
  immediately since `@nestjs/schedule` needs no separate activation step.
- Rollback is deleting/disabling the module (or removing it from
  `AppModule`'s imports) — no data migration to reverse since nothing new is
  persisted.
